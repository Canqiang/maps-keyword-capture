# Automatic UAT store discovery

## Objective

A newly onboarded store with linked keywords should join the next daily capture without editing the monitor config. Existing stores must refresh keywords every day. Preserve the Beijing midnight schedule, keyword text and priority policy, query-only geography, evidence contracts and stable historical prefixes.

## Data flow

1. CronJob creates a Job/Pod at 00:00 Asia/Shanghai.
2. The monitor acquires the date claim. An existing claim exits as `duplicate_skipped` before discovery.
3. A bounded read-only Mongo projection reads `seo-integration.local_keywords`. Validate identities, preserve configured historical aliases, derive stable IDs for new places, and record exclusions.
4. Persist the frozen registry snapshot and its receipt, then checkpoint the daily manifest.
5. For every discovered place, GET the existing keyword API and validate its exact merchant/place identity. Persist a selection snapshot, retaining priority P0–P3, stable source order, exact-text deduplication, and the 40-word cap.
6. Capture batches of up to 20, preserving listings including marked ads, JSON/CSV/screenshots and observations in Azure.
7. Publish the final daily manifest with actual dynamic denominators and separate execution/ranking outcomes.

## Configuration and compatibility

`storeDiscovery` is optional for backward compatibility. Without it, the explicit `stores` list is required and retains static behavior. With it, `stores` may be empty and is only an alias/reference-area map. It never supplies a fallback or allowlist. The UAT release configuration enables provider `mongo`, database `seo-integration`, collection `local_keywords`, 30-second timeout, 10,000-record scan bound and 40-store dispatch bound. Exceeding bounds fails without truncation. Connection details remain in `KEYWORD_MONGO_URI`, excluded from Chromium and evidence. Configuration in the repository does not establish that the running CronJob has been updated; deployment and independent readback belong to the release record.

Discovery includes linked, named records with a nonempty keyword array. Legacy unlinked or empty records are explicitly excluded. The backend has no keyword-record enabled/deleted flag; no invented status policy or mandatory restaurant-location join is applied. An explicit `storeDiscovery.excludedPlaces` list omits approved test places by exact place ID before ownership checks. UAT excludes George Merchant at the user's request, with reason `test_store`; this does not delete source data or exclude other locations by name. Nil/all-zero merchant UUIDs are invalid identities. Duplicate canonical identities and alias ownership conflicts quarantine every record for that place while other eligible stores continue; the monitor never chooses an owner. Invalid alias configuration, source-read failures, identifier collisions and capacity overflows still fail the full discovery. A rename preserves the ID; new place identities produce new deterministic IDs. Registry source hash and config hash are distinct.

Eligibility validates the source's merchant/place linkage and safe identifier format. It rejects legacy UUID/hex identifiers in the place field, but does not independently prove a Google business identity or its local geography. The configured historical aliases retain their original paths; a new store uses `place-` plus the first 32 hexadecimal characters of SHA-256 of its place ID. A source record with no usable name, identity or keyword array is reported in the exclusions instead of silently being counted as captured. Removing or emptying the source record removes that store from a later cycle; there is no separate enabled switch in this release.

## Failure and evidence rules

A global discovery failure must produce an accurate terminal outcome and dispatch no keyword reads or browser work. A quarantined place is omitted from dispatch and retained in the registry evidence. Accepted stores continue, but unresolved quarantine makes overall execution incomplete (exit 2), even when every accepted store finishes. Configured test-store exclusions are intentional scope and do not make execution incomplete. A storage failure while saving discovery/checkpoints also prevents dispatch. Empty discovery is not successful coverage. The registry snapshot and its exact receipt join the existing claim, selection snapshots, batch manifests and artifacts; historical manifests remain readable without a registry field. Roster changes after discovery apply on the following cycle. Keyword edits made before a store's API read can appear in the current cycle; edits after its selection snapshot wait until the next one. Cross-store API reads are fresh sequential reads, not one atomic database transaction.

The daily manifest's optional `registry` section records discovery status, a safe error code, fetched/eligible/excluded counts, quarantined-record counts/reasons, and the snapshot receipt. `quarantined` is a subset of `excluded`, so `fetched = eligible + excluded`; do not add quarantined records again. The snapshot groups quarantines by place with safe source and merchant IDs and records the same reasons on each excluded record. Counts remain unknown until discovery succeeds. The snapshot binds `dailyRunId`, `runKey`, date, live store names, the enrollment policy and exclusions. `configHash` continues to identify the launch configuration and claim; `sourceResponseHash` identifies normalized source identities, exclusions and quarantine groups. Eligible source-document IDs are not retained in the snapshot, so that source hash cannot be reconstructed from the snapshot alone. Its exact file size and SHA-256 are still independently verifiable through the receipt.

## Narrow Apartment rental support in maps-feed-card/v4

The first discovery smoke exposed a real result-card format while searching `float`: a vacation-rental business at display position 10 had a name, `Apartment`, occupancy, directions and amenities, but no rating, review count or address. The v3 parser preserved all evidence and returned `classification_unknown`; the run correctly remained incomplete. Automatic enrollment itself successfully found all eight stores. See the [first-smoke evidence](../evidence/2026-09-23/automatic-store-discovery/README.md).

The resumed release uses `maps-feed-card/v4` to recognize this specific shape. It requires a distinct matching business name, an HTTPS Google Maps place link, the exact `Apartment` category, positive guest/bedroom/bed counts, `Directions`, and at least one of the observed amenities: `Pool`, `Hot tub`, `Free parking`, or `Air-conditioned`. If rendered lines are available, they must agree with the normalized text. Bare `Apartment` cards, other property categories, incomplete occupancy, extra unsupported text and ambiguous ad markers remain unresolved.

An owned `Sponsored` label retains ad precedence and no organic rank. A supported unlabelled card can join the organic sequence; an unresolved card still prevents unsupported downstream organic ranks. Missing rating, review count and address remain `null`. This is support for an observed search-result layout, not a rule that excludes nonrestaurant competitors or treats every apartment result as valid. Existing screenshot coverage, identity, geographic and partial-result boundaries remain unchanged.

The tests reconstruct the visible fields from persisted screenshots and normalized observations; they are not a replay of an archived raw DOM. Local validation of the resumed tree passed typecheck, build and 454 tests across 38 files, including real-browser fixture checks for organic, ad and unresolved variants. The v4 image subsequently passed a separate 8-store / 16-query smoke and full independent evidence readback and was promoted on 2026-09-23; see the release record for exact scope and limitations. Local tests alone do not establish deployment or live capture acceptance.

## Verification scope

Unit tests cover adding/removing stores, stable aliases/renames, identity conflicts, bounded reads/cancellation, empty/failure cases, claim ordering and persistence before dispatch. A UAT smoke exercises the real discovered roster, per-place source reads, browser capture and independent Azure-login readback. The September 23 inventory yielded eight eligible stores and a projected 300 queries / 15 batches at the production cap; the planned two-word-per-store smoke expects 16 selected queries, subject to its fresh snapshots. Neither local validation nor a reduced-cap smoke proves full 300-query or 40-store throughput.

Use a verifier that explicitly supports the actual adapter version and dynamic registry contract. Preserve the original smoke's exit code and partial evidence; do not relabel it after a parser change. The [release evidence](../evidence/2026-09-23/automatic-store-discovery/README.md) records subsequent image builds, actual smoke identities and denominators, all-file Azure verification, visual samples and any final deployment readback separately.
